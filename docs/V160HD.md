# Roland V-160HD LAN / RS-232 control protocol reference

Compiled 2026-09-29 for a Node.js client. Every item is tagged:

- **[DOC]**: stated in an official Roland PDF.
- **[CLIENT]**: what working third-party clients do on real hardware (Companion module, a production fork, a Rust library and a Stream Deck plugin). The behaviour is observed, but Roland does not document it.
- **[UNCERTAIN]**: not established. Verify on a unit.

## 1. Transport

| Item | Value |
|---|---|
| LAN | TCP port **8023** on the LAN CONTROL RJ45 port (100BASE-TX). Roland calls it "Telnet" **[DOC CG p.37]** |
| Telnet option negotiation | None observed. All clients use a raw TCP socket **[CLIENT]**. Whether the device ever sends IAC bytes is **[UNCERTAIN]**; a parser should tolerate and ignore them. |
| RS-232 | DB-9 male, crossover cable, 9600/38400/115200 baud (menu), 8N1, ASCII, no flow control lines (4–6 and 7–8 are looped internally) **[DOC CG p.37]**. The RS-232 SW parameter `02 09 00` must be ON. |
| Simultaneous LAN sessions | **One.** RM p.117 limits the RCS/Remote apps to "LAN connection … up to 1 unit" **[DOC]**. FORK's config warns that only one TCP connection is accepted at a time **[CLIENT]**. CMP issue #21 reports RCS dropping every ~30 s while Companion is also connected **[CLIENT]**. Your client takes the only LAN slot, so RCS over LAN cannot run beside it (RCS over USB may; **[UNCERTAIN]**). |
| Same protocol on RS-232? | Yes. "Commands are common to the LAN and the RS-232 interface" **[DOC CG, BCC]**. Two differences: **STX is mandatory on RS-232** (otherwise `ERR:6`), and there is **no password step on RS-232** (the password is a network password, **[DOC RM]**; that there is no RS-232 prompt is **[UNCERTAIN]** but implied). |

## 2. Login handshake (LAN only)

The **NETWORK PASSWORD** is set at `[MENU] → 23: LAN CONTROL → NETWORK PASSWORD`. It is 4 characters **[DOC CG p.37, RM p.118 menu list]**. CMP's help says a password **must** be set for remote control to work **[CLIENT]**; the menu shows `––––` when none is set.

Exact exchange **[CLIENT, CMP `tcpParser.js`/`api.js`; RRS `authenticate_v160hd`]**:

```
C → S   (TCP connect to :8023)
S → C   "Enter password:"                     no ';', no reliable newline: match as a substring
C → S   "<4-char password>\n"                 e.g. "0000\n" (0x30 0x30 0x30 0x30 0x0A)
S → C   "Welcome to V-160HD."                 no terminator: match as a substring
        (session is now authenticated; send commands)
```

- A wrong password: the device response is **[UNCERTAIN]**. No client handles it. Treat a missing `Welcome` within ~5 s as an auth failure and close the socket.
- Neither prompt appears in Roland's PDFs. The strings come from clients built against real units.
- RRS allows leftover banner text (it saw `Ready\n` before `VER`) and skips anything unparseable before the first frame **[CLIENT, unverified in their own test plan]**.

## 3. Framing

### Outbound (client → V-160HD)

```
[STX 0x02]  CMD  [ ':' param { ',' param } ]  ';'  [LF 0x0A]
```

- **STX (0x02)**: "may be omitted" over LAN (Telnet) and is required on RS-232 **[DOC CG p.38]**. CMP and RRS omit it on LAN. For one code path over both links, always sending STX is legal **[DOC]**.
- **`;`** ends the command **[DOC]**.
- **Trailing `\n`**: CMP and RRS append `\n` after `;` over LAN **[CLIENT]**. Roland does not require it. It is harmless in practice.
- CMP issue #26: `VER` sent **without** `;` produced an error. Always send the `;`.
- The command code is ASCII. In DTH/RQH, addresses and values are **uppercase hex, 2 chars per byte** (the device also emits uppercase).

### Inbound (V-160HD → client)

- Responses are ASCII frames ending in `;`. BCC says "a carriage return code (0x0A, LF) is sent after the semicolon" on responses **[DOC BCC p.2]**.
- A response **may** start with STX 0x02 **[DOC CG shows `stxDTH:…`]**. Strip leading 0x02.
- **XON 0x11 / XOFF 0x13** are defined flow-control codes and may appear in the stream **[DOC CG]**. Strip them. Honouring XOFF on RS-232 is prudent.
- **ACK: two documented spellings. Handle both:**
  - CG (SysEx wrapper commands): reply `ack` = the single control byte **0x06** **[DOC]**.
  - BCC (basic commands): reply is the ASCII text **`ACK;`** + LF **[DOC]**.
  - CMP filters ASCII `ACK` tokens, which implies the unit sends ASCII `ACK;` for DTH too **[CLIENT]**. RRS accepts 0x06, `ACK`, and `ACK;` **[CLIENT]**. Which one v3.x firmware sends for `DTH` is **[UNCERTAIN]**. Parse both.
- A robust tokenizer: drop 0x02/0x11/0x13/CR/LF/NUL/0xFF-IAC noise. Treat a lone 0x06 as an ACK frame. Otherwise split on `;`. Keep the pre-auth substring matching from §2.

### Errors **[DOC CG p.38, BCC p.45]**

`ERR:a;`, where a =

| a | Meaning |
|---|---|
| 0 | syntax error |
| 4 | invalid (no effect because another setting overrides it) |
| 5 | parameter out of range |
| 6 | missing STX (**RS-232 only**) |

## 4. Two command dialects on the same socket

The V-160HD accepts **both** of these, freely mixed ("You can use the basic control commands at the same time as the regular commands" **[DOC BCC p.2]**):

1. **SysEx-wrapper commands** (all firmware): `DTH` = write and `RQH` = read, against the MIDI SysEx parameter address map, plus `VER`. **[DOC CG]**
2. **Basic control commands** (firmware **≥ 3.3**, extended at **3.5**): mnemonic, human-readable tokens such as `PGM:HDMI1;`, `CUT;`, `QPGM;`, `TLY;` **[DOC BCC]**. The BCC cover lists "Version 3.5 and later / 1.3 / 2.2 / 2.2 / 1.0". The products are listed in the order V-160HD / V-80HD / VR-120HD / VR-6HD / V-1-4K, so V-160HD = 3.5 (eng01: 3.3). That pairing comes from the listing order and is slightly **[UNCERTAIN]**.

Neither real client uses the basic commands yet (CMP, FORK, RRS and SD all use DTH/RQH). The basic-command responses have **not** been confirmed by any client on hardware **[UNCERTAIN]**. Check the firmware first with `VER;`.

### 4a. SysEx wrapper syntax **[DOC CG p.38]**

| Purpose | Send | Reply |
|---|---|---|
| Write parameter | `DTH:aaaaaa,vv;` (address = 3 bytes, 6 hex chars; value = hex; multi-byte values are hex concatenated) | ACK (0x06 or `ACK;`, see §3) |
| Read parameter | `RQH:aaaaaa,ssssss;` (size = 3 bytes, 6 hex chars) | `DTH:aaaaaa,vv…;` (one hex pair per byte, starting at the address) |
| Version | `VER;` | `VER:V-160HD,x.xx;` **[DOC]**. RRS also accepts `VER:V-160HD:x.xx;` defensively **[CLIENT, unverified]**, and an `ACK` may come first. |

Multi-byte reads work. For example, `RQH:002100,000002;` → `DTH:002100,PPVV;` gives PGM and PST in one frame **[CLIENT, FORK TESTING.md "confirmed live" for 2-byte reads]**. On a read with a bad address or size, "the unit sends nothing" **[DOC CG p.2, the RQ1 rule]**, so time out reads (FORK dropped `RQH:000110` because it never answers **[CLIENT]**). 14-bit values are 2 × 7-bit bytes, MSB first (`aa*128+bb`) **[DOC CG p.35]**.

## 5. Source numbering

### 5a. SysEx source code (PGM/PST select, PinP source, tally index) **[DOC CG p.8 "Panel", p.32 "Tally"]**

| Code (hex) | Source | Basic-command token |
|---|---|---|
| `00`–`07` | HDMI 1–8 | `HDMI1`…`HDMI8` |
| `08`–`0F` | SDI 1–8 | `SDI1`…`SDI8` |
| `10`–`1F` | STILL 1–16 | `STILL1`…`STILL16` |
| `20`–`33` | INPUT 1–20 (the logical cross-point channels) | `INPUT1`…`INPUT20` |

- Tokens have **no space** (`HDMI1`, not `HDMI 1`) **[DOC BCC]**.
- The INPUT n → physical assignment is `00 00 00`–`00 00 09` (INPUT 1–10) and `00 00 24`–`00 00 2D` (INPUT 11–20, **[CLIENT CMP/FORK]**; CG p.3 shows only INPUT 1–10 at `000000`–`000009`). The value is `00`–`1F` = HDMI/SDI/STILL, or `20` = N/A **[DOC]**. Basic form: `QVIS:INPUT1;` → `VIS:INPUT1,HDMI1;ACK;`.
- When the bus holds an INPUT n, `QPGM`/`QPST` return the physical source **and** the INPUT, e.g. `PGM:HDMI2,INPUT2;ACK;` **[DOC BCC]**. Whether `RQH:002100` returns the `2x` INPUT code or the physical code after an INPUT select is **[UNCERTAIN]**. CMP resolves `20`–`33` through the assign table, so it expects `2x` codes to come back.

### 5b. Panel cross-point buttons

`0B 00 00`–`0B 00 09` = PGM/A buttons 1–10, `0B 00 0A`–`0B 00 13` = PST/B buttons 1–10 **[DOC CG p.31]**. These are physical button positions, not sources.

## 6. Command table: what you asked for

`P` = SysEx wrapper (all firmware), `B` = basic command (fw ≥ 3.3/3.5).

| Function | Dialect | Send | Expected reply |
|---|---|---|---|
| **PGM select** | P | `DTH:002100,<code>;` e.g. `DTH:002100,08;` (SDI 1) | ACK |
| | B | `PGM:SDI1;` (HDMI1–8, SDI1–8, STILL1–16, INPUT1–20) | `ACK;` |
| **PST select** | P | `DTH:002101,<code>;` | ACK |
| | B | `PST:HDMI3;` | `ACK;` |
| **CUT** | B | `CUT;` (only when SPLIT is OFF) | `ACK;` |
| | B | `CUT:<src>;` cuts straight to that source | `ACK;` |
| | P | panel press/release: `DTH:0B001E,01;` then ~200 ms later `DTH:0B001E,00;` | ACK, ACK |
| **AUTO** | B | `ATO;` (SPLIT OFF; uses the set transition time) | `ACK;` |
| | B | `ATO:<src>;` or `ATO:<src>,<t>;`, where t = `-1` (use the set time) or `0`–`40` (0.0–4.0 s) | `ACK;` |
| | P | `DTH:0B001F,01;` then `DTH:0B001F,00;` | ACK, ACK |
| **Query PGM** | P | `RQH:002100,000001;` | `DTH:002100,<code>;` |
| | B | `QPGM;` | `PGM:<phys>[,INPUTn];ACK;` |
| **Query PST** | P | `RQH:002101,000001;` | `DTH:002101,<code>;` |
| | B | `QPST;` | `PST:<phys>[,INPUTn];ACK;` |
| PGM+PST together | P | `RQH:002100,000002;` | `DTH:002100,<pgm><pst>;` |
| **Auto transition running?** | B | `QATG;` | `ATG:ON;ACK;` / `ATG:OFF;ACK;` |
| Fader level | P | `RQH:002102,000002;` (14-bit, 0–2047) | `DTH:002102,hhll;` |
| | B | `QVFL;` / `VFL:0..2047;` | `VFL:n;ACK;` / `ACK;` |
| A/B bus select, dissolve take type | P | `002104` (A/B), `002105` (CUT/AUTO) | |
| Transition type/time | P | `001800` MIX/WIPE; `001700` MIX/WIPE time `00`–`28` (0.0–4.0 s) | |
| | B | `TRS:` / `QTRS;`, `TIM:` / `QTIM;` | |
| **Tally (all sources)** | B | `TLY;` | `TLY:a0,a1,…,a51;ACK;` (order: HDMI1–8, SDI1–8, STILL1–16, INPUT1–20; 0 = off, 1 = PGM, 2 = PST, 3 = both) |
| | P | `RQH:0C00xx,000001;` (xx = source code `00`–`33`) | `DTH:0C00xx,0n;` |
| Busy | B | `QBSY;` | `BSY:ON;` / `BSY:OFF;` (no ACK documented) |
| Version | P/B | `VER;` | `VER:V-160HD,3.xx;` (+`ACK;` per BCC) |
| Ping / keepalive | B | `ACS;` ("Return ACK") | `ACK;` |
| Input signal status | B | `QVIST:HDMI1;` | `VIST:HDMI1,DETECTED;ACK;` (NOSIGNAL/DETECTED/UNSUPPORTED) |
| Input assign | P | `RQH:000000,00000A;` / `RQH:000024,00000A;` | 10-byte blocks |
| | B | `QVIS:INPUTn;` / `VIS:INPUTn,<src>;` | |
| Memory recall | P | `DTH:0A0000,<00–1D>;` | ACK |
| | B | `MEM:MEMORY1;`, `QMEM;` | |

**Panel press semantics [CLIENT]**: CMP and RRS both send press `01`, sleep 200 ms, then release `00`. Roland documents only "Release, press (Write only)" **[DOC]**. What CUT/AUTO actually do depends on the **CUT/AUTO SW ASSIGN** system settings (`02 01 0E` / `02 01 0F`: AUDIO TAKE, AUTO TAKE, CUT, TRANSFORM…) and on the **operation mode** (PGM/PST, A/B, DISSOLVE, PGM/PST(20); **[DOC CG, RM p.17]**). Prefer `CUT;` / `ATO;` when the firmware has them.

**Mode caveat [DOC RM p.17]**: in **A/B mode**, CUT/AUTO alternate which of PGM/A or PST/B is on air. "PGM" in the address map is the PGM/A *bus*, which may not be the on-air source. In DISSOLVE mode a select goes straight to PGM. For "what is on air", trust tally or `QPGM` over the `002100` register when not in PGM/PST mode. Whether `002100` tracks the on-air bus in A/B mode is **[UNCERTAIN]**.

## 7. Source names

- **Per-source labels (the multi-view LABEL EDIT)**: 8 ASCII chars at `02 xx 00`–`02 xx 07` **[DOC CG p.29]**, where xx is:
  - `10`–`17` = HDMI 1–8, `18`–`1F` = SDI 1–8, `20`–`2F` = STILL 1–16, `30` = PGM, `31` = SUB PGM, `32` = PVW, `33` = AUX 1, `3A`–`3B` = AUX 2–3, `3C`–`3D` = DSK 1–2 SOURCE.
  - The per-source mapping (xx = source code + 0x10) is derived from the range list "10H–33H (HDMI 1–8, SDI 1–8, STILL 1–16, PGM, SUB PGM, PVW, AUX 1)". It follows from the doc but is untested **[UNCERTAIN]**.
  - Read: `RQH:021000,000008;` → `DTH:021000,<16 hex chars>;` (ASCII bytes 00–7F). Strip trailing NUL/space: FORK found the memory names come back NUL-padded (`MEMORY1\0`) **[CLIENT]**, and labels likely do the same.
  - **INPUT 1–20 have no names of their own.** Show the label of the physical source assigned to them (§5a).
- **Preset memory names**: `RQH:60xx00,000008;`, xx = `00`–`1D` (Memory 1–30) **[DOC CG p.34]**.
- The **basic commands have no label query** **[DOC BCC]**.
- Labels are not pushed. Read them at connect and on demand. **Do not poll names continuously**: CMP issue #26 traced dropped commands to polling 240 name-character requests per cycle **[CLIENT]**.

## 8. Push notifications (tally)

- **Enable**: `DTH:0C0100,01;` = "TALLY AUTO SEND ON" at `0C 01 00` (OFF/ON) **[DOC CG p.33]**. The section is misprinted "Tally Audio Send"; the parameter name is TALLY AUTO SEND.
- **What arrives [CLIENT CMP + FORK]**: unsolicited `DTH:0C0000,<hex bytes>;`, **one frame carrying the whole tally table** from `0C0000` up. There is one byte per source in the §5a order. FORK comments "device pushes this on every source change" and has 52 entries (HDMI 1–8, SDI 1–8, STILL 1–16, INPUT 1–20). The older CMP table has 42 entries (…, XPT 1–10) from firmware with 10 inputs. **Parse by the frame's length** and never assume a fixed size. RRS also accepts single-byte `DTH:0C00xx,vv;` notifications defensively.
- **Byte value**: `00` OFF, `01` PGM, `02` PST, `03` PGM & PST **[DOC CG p.32]**. Treat it as bit 0 = PGM, bit 1 = PST (CMP does).
- **Enable reply**: SD and RRS report the unit "often never ACKs" `DTH:0C0100` and send it fire-and-forget. Blocking on that ACK stalled their only session **[CLIENT]**. Do not wait on an ACK for this write.
- **Scope**: whether the subscription persists across reconnects or power cycles is **[UNCERTAIN]**. Send it after every successful login (every client does).
- **Tally ≠ bus source**: tally reflects everything on air. The **TALLY SETTINGS** (`02 09 43`–`02 09 4B`: AUX 1–3, PinP & KEY 1–4, DSK 1–2, each DISABLE/ENABLE) decide whether sources used in PinP, DSK or AUX also light PGM **[DOC CG p.28]**. Several sources can therefore be "PGM" at once. To get the exact PGM/PST **bus** selection, treat each tally push as a trigger and immediately read `RQH:002100,000002;` (or `QPGM;` + `QPST;`). FORK does exactly this **[CLIENT]**.
- **Nothing else is pushed**: FORK TESTING.md says there is no push for AUX source changes. BCC's "Commands voluntarily sent" table lists only `ACK;` and `ERR:a;`. For everything except tally, poll.

**Recommended loop**: login → `VER;` → `DTH:0C0100,01;` → an initial `RQH:002100,000002;` + `TLY;` (or `RQH:0C0000,000034;`, **[UNCERTAIN]**, since only 1- and 2-byte and 16-byte reads have been exercised) → then on each `DTH:0C0000` push re-read `002100`/`002101`. Add a slow safety poll (e.g. `RQH:002100,000002;` every 2–5 s), which also serves as the keepalive.

## 9. Transition-state feedback

- `QATG;` → `ATG:ON|OFF` reports whether an auto transition is in progress **[DOC BCC]**. Its exact semantics ("Auto Transition in use") are not specified further.
- `RQH:002102,000002;` / `QVFL;` give the A/B fader level (0–2047) **[DOC]**. The effect of AUTO on the fader level readback is **[UNCERTAIN]**.
- **Mid-AUTO values of `002100`/`002101`, `QPGM` and tally are not documented** **[UNCERTAIN]**. By analogy with Roland's other switchers, tally probably shows both outgoing and incoming sources as PGM during the mix, and the PGM/PST registers probably swap on completion. Neither is confirmed. To settle it, log `002100` + tally + `QATG` at 50 ms intervals during a 2 s AUTO on a real unit.
- CMP issue #19: when the same source is on PGM and PST, tally reads `03`. A tally state machine must treat `03` as PGM.

## 10. Rate limits and flow control

- **[DOC CG p.2]**: for SysEx Data Set, "set interval of 20 msec or longer between packets" and split data over 256 bytes into ≤ 256-byte packets. CMP applies ≥ 20 ms between `DTH` writes **[CLIENT]**.
- CMP batches reads 4 at a time, 5 ms apart **[CLIENT]**. Even so, CMP issues #21/#26 show the unit **silently dropping commands** under heavy polling (hundreds of RQH per cycle). Users saw multi-press failures.
- **Recommendation** (not documented): keep one command in flight and wait for its ACK/DTH/ERR, with a timeout of about 500 ms–1 s, since RQH with a bad address never answers. Keep ≥ 20 ms between writes, and keep steady-state polling to a handful of reads per second. Honour XOFF (0x11/0x13) on serial.
- `QBSY;` exists to check whether the unit is busy (e.g. loading a memory) **[DOC BCC]**. Whether commands are rejected while busy is **[UNCERTAIN]**.

## 11. Keepalive / idle timeout

- No keepalive or idle timeout is documented **[DOC]**. CMP relies on its polling. Its TCPHelper reconnects 30 s after a close **[CLIENT]**.
- `ACS;` → `ACK;` is an official no-op "Return ACK" **[DOC BCC]** and makes a good ping on fw ≥ 3.3. Below that, use `VER;` or `RQH:002100,000001;`.
- Whether the device drops an idle authenticated session is **[UNCERTAIN]**. Set TCP keepalive on the socket and ping every ~10 s.

## 12. Sibling models

| Model | Same protocol? |
|---|---|
| **V-80HD, VR-120HD, VR-6HD, V-1-4K** | Share the **Basic Control Commands** document (BCC) with the V-160HD. Their source token lists differ. They also have DTH/RQH SysEx wrappers against their own address maps (e.g. the V-80HD Control Guide: https://static.roland.com/assets/media/pdf/V-80HD_Control_eng01_W.pdf). The VR-6HD uses Telnet port 23 per RRS **[CLIENT]**. Login prompts on these models were not checked **[UNCERTAIN]**. |
| **V-60HD** | **Different protocol.** Also TCP **8023**, but **no password**, **STX mandatory on LAN too**, and ACK is the **0x06** byte. It uses 3-letter opcodes with numeric channels (`\x02PGM:0;`, `\x02PST:a;`, `\x02CUT;`, `\x02ATO;`, `\x02TLY;`, `\x02QPL:7;`) **[DOC V60 LAN/RS-232 section; CLIENT companion-module-roland-v60hd, RRS]**. One connection only. RRS's hardware check on fw 3.02 saw a *duplicate* ACK after commands and no unsolicited TLY/QPL. V60 does document a setting that sends `QPL:7` automatically on RS-232. |
| **V-8HD** | Has **no LAN/RS-232 control**: USB (the V-8HD Remote iPad app) and MIDI only (Roland support search result; the V-8HD reference manual has a MIDI Implementation chapter). Lightly checked; confirm against the V-8HD manual if it matters. |

## 13. Uncertain items (verify on hardware)

1. ACK form for `DTH` writes on current firmware: the byte `0x06` or the text `ACK;`, and whether an LF follows.
2. The exact reply to a wrong password, and behaviour when no password is set.
3. Tally push frame length on fw 3.x (expected 52 bytes = 104 hex chars). Is there exactly one frame per change, and does it fire for front-panel changes (FORK says yes)?
4. Whether `DTH:0C0100,01` survives reconnect or power cycle, and whether it is ever ACKed.
5. `002100`/`002101` readback after selecting INPUT n: is it the `2x` code or the physical code? Behaviour in A/B and DISSOLVE modes.
6. PGM/PST/tally values during an AUTO transition. Whether `QATG` is the reliable in-progress flag.
7. The basic-command replies (`QPGM`, `TLY`, `ATG`) have not been confirmed by any public client on hardware. They need fw ≥ 3.3 (3.5 for the eng02 set).
8. Label address mapping `02 (code+10H) 00` and NUL/space padding.
9. Large multi-byte reads (e.g. `RQH:0C0000,000034;`). Documented in principle, but only 1-, 2- and 16-byte reads have been used by clients.
10. Idle-session timeout, and whether Telnet IAC negotiation is ever sent.
11. Whether RCS over USB can run while a LAN client is connected.
12. The `VER` reply separator (`,` is documented; RRS defensively accepts `:`).
